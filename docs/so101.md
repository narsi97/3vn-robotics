# The SO-101, as a second robot

```bash
make so101-fetch                        # once
make sim      PROFILE=so101_follower    # in Gazebo
make scenario NAME=all                  # in a second terminal
```

The SO-101 is TheRobotStudio's open arm: five joints and a jaw, six
STS3215 bus servos, Apache-2.0. Nobody here designed it. It runs under
this project's controllers, client, scenarios and test suite, and the
only thing that names it is `PROFILE`.

[The spike](so101-spike.md) is how that started, and what it broke.
This page is what it became.

## A profile that is an overlay

The 3VN arm's profile is the source of its physical truth: every length,
mass and limit is in the YAML, and the URDF is generated from it.

The SO-101 already has a URDF. Copying its numbers into a profile would
create a second copy that could disagree with the first, with nothing to
say which was right. So `so101_follower.yaml` restates **no** kinematics.
It adds only what a URDF has no place for:

| In the profile | Why |
|---|---|
| Which joints are the arm, and which is the gripper | Nothing in a URDF says so |
| How far the gripper opens and closes | It is a revolute jaw, in radians; the 3VN arm's is prismatic, in metres |
| Named poses | Five numbers each, for this arm |
| The servo's datasheet figures | Upstream's limits are placeholders |
| The execution targets | `mock`, `gz` and `feetech` |

`describe()` puts the two together at launch, in memory. The file in
`vendor/` is never edited.

```bash
make urdf PROFILE=so101_follower | less
```

## What the overlay changes, and why

**It anchors the arm.** Upstream has no `world` link, so its base is a
free body, and a 632 g arm falls over the first time a joint moves. A
real one is clamped to a bench. The overlay is that clamp.

**It replaces the limits.** Upstream declares `effort="10"` on every
joint. An STS3215 stalls at about 1.9 N·m, so the arm as shipped is five
times stronger in simulation than on the bench: a motion that succeeds
in Gazebo and stalls in reality. The overlay derives effort and velocity
from the datasheet, the same rule the 3VN arm follows. Position limits
are upstream's, untouched.

**It simplifies what the physics sees.** Upstream's collision geometry
is its visual geometry: full printed-part meshes, most of them tens of
thousands of triangles. Measured here, on CPU physics:

| Collision geometry | Real-time factor |
|---|---|
| Upstream's meshes | 0.11 to 0.13 |
| Each mesh's bounding box | 0.91 to 1.03 |

The simulator tier of the test suite refuses anything under 0.3. A
bounding box is never smaller than the part, so it errs toward a contact
that would not quite have happened. It is too coarse for the jaws to
close on something small; a grasp will want the two jaw links back as
meshes.

**It gives the joints friction.** Upstream declares none, so every
joint is a frictionless hinge. That was invisible until the jaw was
closed with the gripper pointing down. Gravity helped it along, which
held it at exactly its velocity limit, and it ran through "closed" into
its hard stop and never moved again. The physics engine gives each joint
one constraint, in the order position limit, velocity limit, servo: a
joint sitting on a limit is not being driven at all. Level, gravity does
not act about that axis, and everything worked.

The `pick_and_place` scenario passed throughout. Its release step was a
bare wait with no check, and the gripper action "succeeded" by stalling.
The step has a check now, and with the friction removed it fails.

One piece of this is still there. A joint commanded exactly onto a hard
stop in Gazebo can stay on it. The gripper's named travel keeps clear of
both stops, and the teleop uses that travel, so the ordinary commands
never do it; sending the jaw to its raw upper limit by hand still can.

**It says what the robot is.** A `<threevn_semantics>` element carries
the arm's joints, the gripper's travel and the named poses inside the
description. The client reads them from `/robot_description`, where it
already reads the joint limits. So a client attached to a running robot
gets that robot's poses without being told which profile launched it.

```bash
make urdf PROFILE=so101_follower | grep -A9 threevn_semantics
```

## The description is a dependency, so it has a version

`make so101-fetch` used to pull from upstream's `main`. A joint renamed
there would have failed tests here with nothing changed in this
repository. It now fetches one commit and checks the URDF's SHA-256
before installing it. Taking a newer upstream is a deliberate change:
move the pin, read the diff, run the suite, then update the checksum.

## The same suite, another robot

```bash
make test-ros PROFILE=so101_follower
make test-sim PROFILE=so101_follower
```

These are the 3VN arm's integration tests. They name no joint: they read
the joints, limits, frames and poses out of the description of whichever
robot `PROFILE` is. One test is skipped on the SO-101 and says why: the
3VN arm's home position can be added up by hand from its YAML, and a
foreign arm's cannot.

Running them found something the mock target could not. The `move_joint`
scenario used to jog each joint and leave it there. On the 3VN arm, with
hand-picked targets, that was survivable. On a longer arm three small
jogs forward put the gripper through the bench, and only physics
noticed. Each joint now returns before the next moves.

## The swap point

```bash
make mock PROFILE=so101_follower      # target: mock
make sim  PROFILE=so101_follower      # target: gz
                                      # target: feetech  (the physical arm)
```

`feetech` is declared in the profile and described by `describe()`: the
plugin name, the serial endpoint, the baud rate and each servo's bus id.
**The hardware interface behind it is not written yet.** That is the
same position `esp32` was in before the firmware existed, and for the
same reason: fixing the name and the parameters first is what confines
the rest to one plugin.

When it exists, moving from the virtual arm to the real one is that one
argument. The controllers file, the topics, the actions and the six
scenarios do not change.

## What does not work yet

- Inverse kinematics. The closed form [refuses](so101-spike.md) a
  five-joint chain, correctly. The SO-101 needs a numerical solver.
- Grasping, which needs the solver and mesh collisions on the jaws.
- A camera. This description has none.
- `make play`, which is wired to the mobile manipulator.
